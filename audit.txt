# AUDIT COMPLET & PLAN DE REFONTE — catalog.discado.ch

**Date :** 2026-02-17
**Racine projet :** `/sites/catalog.discado.ch/`
**Stack :** Node.js + Express.js + SQLite3 + Vanilla JavaScript
**Score global :** 3.5/10

---

## CONTEXTE

catalog.discado.ch est un catalogue B2B de produits (gadgets, accessoires) construit sur Node.js + Express + SQLite. Il gère un catalogue client, un système de commandes, la facturation PDF avec QR suisse, la gestion des fournisseurs, et une comptabilité intégrée. L'application fonctionne mais souffre de vulnérabilités de sécurité critiques, d'un fichier monolithique de 3 087 lignes (`index.js`) contenant les 119 routes, de fichiers JS frontend dépassant 700 lignes, de code dupliqué entre les panneaux public et admin, d'aucun test, et de dettes techniques accumulées. Ce plan vise à sécuriser, restructurer et moderniser le site sans interruption de service.

## PARTIE 1 — RAPPORT D'AUDIT

### 1.1 — Scores par domaine

| Domaine | Score | Verdict |
|---------|-------|---------|
| Structure & Architecture | 3/10 | Monolithe `index.js` (3 087 lignes, 119 routes). Services dupliqués (`invoiceService.js` + `InvoiceService2.js`). Compteur de commandes dans un fichier JSON séparé de la DB. dotenv commenté. |
| HTML (sémantique, accessibilité, SEO) | 3/10 | Pas de `<meta description>`, pas d'Open Graph, `lang` incohérent (en/fr), `user-scalable=no` bloque le zoom, aucun ARIA, aucun skip-nav. |
| CSS (architecture, responsive, perf) | 4/10 | `.category-item` dupliqué dans 5 fichiers CSS. Deux versions Font Awesome (5.15.4 + 6.4.0). Palette incohérente (`#2575fc` vs `#f44336`). z-index anarchiques (999-1060). Pas de minification. |
| JavaScript (organisation, sécurité, perf) | 4/10 | Architecture modulaire propre (core/modules/utils) — bon point. Mais 14 fichiers dépassent 200 lignes (jusqu'à 744). 35+ `innerHTML` sans sanitization (XSS). Code dupliqué entre public/ et admin/ (formatter, modal, notification, storage, validation). `csurf` importé mais jamais activé. Winston importé mais jamais utilisé. |
| Base de données | 4/10 | Requêtes paramétrées à 99%. Mais compteur de commandes hors DB (race condition). JSON dans colonnes TEXT (fournisseurs non normalisés). N+1 dans `orderService.js`. 3 fichiers DB dont 2 vides. |
| Sécurité | **2/10** | Path traversal exploitable, CSRF absent, mots de passe en clair supportés, clés de chiffrement regénérées au redémarrage et loggées en console, pas de régénération de session. |
| Performance | 5/10 | Pas de lazy loading images, pas de minification CSS/JS, pas de cache HTTP, pas de pagination sur les listes. |
| Maintenabilité & Qualité | 3/10 | Zéro test. Pas de linter. Pas de TypeScript. Code mort non nettoyé. Package nommé "mon-projet". Pas de README. |

### 2.3 — Recommandation framework

**Rester sur Express.js + JavaScript vanilla.** Le problème n'est pas le framework mais l'organisation. Le frontend modulaire existant (core/modules/utils) est propre. Migrer vers React/Vue apporterait zéro valeur métier pour un catalogue B2B à audience limitée. L'ajout progressif de TypeScript (backend d'abord) est recommandé à terme.

## PARTIE 5 — RISQUES ET MITIGATIONS

| Risque | Impact | Probabilité | Mitigation |
|--------|--------|-------------|------------|
| **Casser la production pendant la refonte** | Critique | Élevée | Initialiser Git avant toute modification. Chaque phase = branche séparée. Garder `index.js` original en backup. Smoke tests manuels systématiques après chaque phase. |
| **Perte de données lors des migrations DB** | Critique | Moyenne | Backups quotidiens déjà en place (`/database_discado/`). Backup manuel supplémentaire avant Phase 5. Tester chaque migration sur une copie de la DB. Écrire des scripts de rollback pour chaque migration. |
| **Invalidation des sessions lors du changement de clés** | Moyen | Élevée | Planifier Phase 1.4 en heures creuses. Une fois les clés persistées dans `.env`, c'est un événement unique. Communiquer aux utilisateurs qu'une reconnexion sera nécessaire. |
| **CSRF casse les formulaires frontend** | Moyen | Moyenne | Implémenter le token CSRF via meta tag + endpoint `/api/csrf-token`. Mettre à jour tous les `fetch()` du frontend pour inclure le token. Tester chaque formulaire et chaque appel AJAX. |
| **Migration mots de passe bloque les utilisateurs** | Élevé | Faible | Identifier les comptes avec mots de passe en clair avant migration. Vérifier le login de chaque compte affecté après migration. Garder le fallback plaintext 48h avec monitoring, puis supprimer. |
| **Scope creep Phase 2 (restructuration backend)** | Moyen | Élevée | Phase 2 = déplacer le code, PAS réécrire la logique. Les contrôleurs doivent initialement juste wrapper les appels aux services existants. Deadline dure : si > 2 semaines, livrer l'état actuel. |
| **Régression lors de la compartimentalisation JS (Phase 4)** | Moyen | Élevée | Éclater un fichier à la fois, tester après chaque éclatement. Les imports ES6 sont vérifiables statiquement. Garder les anciens fichiers jusqu'à validation complète. |
| **Absence de filet de sécurité (zéro test)** | Élevé | Certaine | Écrire 4-5 smoke tests basiques (serveur démarre, login fonctionne, produits chargent, commande crée) AVANT de commencer la Phase 2. Ce filet minimal protège contre les régressions majeures. |

## PARTIE 6 — DÉCISIONS TECHNIQUES CLÉS

| Décision | Justification |
|----------|---------------|
| **Rester sur Express.js** | Le problème est organisationnel, pas lié au framework. Express convient parfaitement à un catalogue B2B. Migrer vers Fastify ou NestJS n'apporterait pas de valeur proportionnelle à l'effort. |
| **Rester en vanilla JS côté frontend** | L'architecture modulaire existante (core/modules/utils) est propre et bien pensée. React/Vue n'apporterait aucune valeur métier pour un catalogue B2B à audience limitée. Le coût de migration serait disproportionné. |
| **Rester sur SQLite** | Base de données < 4 Mo, usage mono-serveur, pas de requêtes concurrentes intensives. SQLite en mode WAL est largement suffisant. Migration vers PostgreSQL non justifiée à cette échelle. |
| **Pas de TypeScript immédiat** | Priorité aux corrections de sécurité et à la restructuration. TypeScript pourra être ajouté progressivement après Phase 8, en commençant par le backend (services + controllers). |
| **Couche `shared/` dans public/js/** | Plutôt qu'un dossier séparé à la racine, placer `shared/` dans `public/js/` permet aux modules admin d'y accéder via des chemins relatifs (`../../public/js/shared/`) tout en gardant les assets statiques servis par Express. |
| **csurf pour le CSRF** | Déjà installé dans les dépendances npm. Solution éprouvée avec Express. Pas besoin d'ajouter une nouvelle dépendance. |
| **Winston pour le logging** | Déjà installé dans les dépendances npm. Support fichier, rotation, niveaux de log. Remplace les `console.log` éparpillés. |
| **Jest pour les tests** | Standard de facto pour Node.js. Supertest pour les tests d'intégration HTTP. Large écosystème et documentation abondante. |
